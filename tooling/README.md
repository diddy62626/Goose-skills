# tooling

**Tooling** — The goose CLI, run vs build, diagnostics, packages, editors/LSP, compiler internals, testing.

8 skills. Load any of them as `tooling/<skill>/skill.md`.

- [`goose-cli-reference`](tooling/cli-reference/skill.md) — CLI reference — every goose command and option: > The complete goose command surface: run/build/check/fetch/format/lsp/ toolchain/version/completion/help; shared options (-O0..-O2, --debug, -D, --stack-reserve, --stacks, --bce-lines, --specs, --stats, --diagnostics json, --offline); runtime -D macros; environment variables; exit codes; and the compiler-internals flags.
- [`goose-compiler-internals`](tooling/compiler-internals/skill.md) — Compiler internals — whole-program model, specialization, generated C: > Goose compiles the whole program (closed world) in call-graph order: it computes the data stacks, specializes functions per root/constness/ types, generates C, and links a once-compiled runtime. What agents should know: no separate compilation, static function values, the roots analysis, BCE, --specs/--dump inspection, and the goose-in-goose self-hosting bootstrap.
- [`goose-diagnostics`](tooling/diagnostics/skill.md) — Compiler diagnostics — reading errors, JSON output, stats: > How the compiler reports problems: stderr with source line and caret, both-ends error messages (reference + binding site, holder + store site, instantiation + call chain), --diagnostics json shape for tools, --stats and --bce-lines output, color control, and where progress notes go.
- [`goose-editors-lsp-format`](tooling/editors-lsp-format/skill.md) — Editors, the language server, and goose format: > The compiler is its own language server (goose lsp over stdio): diagnostics as you type, hover, go-to-def, references, rename, semantic tokens, inlay hints, code lenses with instantiation counts and Run. VS Code extension; Neovim/Helix/Emacs configs; entryFiles initialization option; goose format rules and format-on-save per editor.
- [`goose-making-a-package`](tooling/making-a-package/skill.md) — Making and publishing a Goose package: > Package layout (entry module with the package's namespace), the requirement rule for a library's own dependencies, examples and tests as root files, extern blocks for machine libraries, embed_file for shipped data, and the publish workflow (push, tag, tell users the import line).
- [`goose-packages`](tooling/packages/skill.md) — Packages — declaring, fetching, pinning dependencies: > import name from "owner/repo@v1"; (or a directory) declares a package in the program's root file. Only the root declares; other files' declarations are requirements the root must satisfy. Tags/commits pin; branches need --update. goose fetch pre-fetches; --offline forbids fetching. The ~/.goose cache layout.
- [`goose-run-build-backends`](tooling/run-build-backends/skill.md) — run vs build — the two backends and when each works: > goose run compiles to C and runs it in-process via TinyCC (no files, no C compiler needed beyond libc headers); goose build uses a real C compiler (optimized -O2 C, executables beside the source). What each can and cannot do: threads need a build, extern symbols resolve differently, timing needs a build, --debug for checked builds.
- [`goose-testing-debugging`](tooling/testing-debugging/skill.md) — Testing and debugging Goose programs: > How to test and debug Goose code: assert-based tests with panic-style aborts, --debug builds that name failing checks and values, clean runtime abort messages with source lines, GS_DEBUG/GS_STACK_STATS knobs, --multi- test for batch-checking files, and the repo's own test suite conventions (expected output, // error: markers).
