# data-modeling

**Working with data** — Inline nested data, index types, linked structures, root structs, pools, serialization.

7 skills. Load any of them as `data-modeling/<skill>/skill.md`.

- [`goose-index-for-sequential-arrays`](data-modeling/index-for-sequential-arrays/skill.md) — Index for sequential arrays — random access into packed data: > An array of variable-size elements can be walked but not indexed. Keep a second array of 4-byte links (in pool, global) or 8-byte plain references (local) beside it, pushed alongside each element, to reach any element in any order.
- [`goose-index-types`](data-modeling/index-types/skill.md) — Index types — `u32 in nodes` and checkfree functions: > An index type uN in a is an unsigned integer proven below a.len wherever observed; the check moves to where the index enters the program (x as NodeId aborts if out of range). Indexing a with its own index type needs no bounds check — the basis of checkfree graph traversal. Bound types (uN upto a) for range ends.
- [`goose-inline-nested-data`](data-modeling/inline-nested-data/skill.md) — Inline nested data — varint records, byte counting, sequential trade-offs: > Structs keep variable-size parts inline in declaration order; varint fields shrink integers to their value's length. A whole order book is one packed array of orders with no pointers. The 29-byte order worked example, when to use variable-size elements (walked data) vs fixed (indexed data).
- [`goose-linked-structures`](data-modeling/linked-structures/skill.md) — Linked structures — trees, lists, ASTs in pools with typed links: > Where Rust uses Vec<Node> + u32 indices and C++ uses pointers, Goose puts nodes in one grow-only array and links them with typed (often narrow) references that survive growth. BST insert, doubly-linked list with a self sentinel, variable-mode enum ASTs at 23 bytes, and the recursion rules for walking them.
- [`goose-root-structs`](data-modeling/root-structs/skill.md) — Root structs — several independently growing fields under one owner: > An ordinary struct holds at most one resizable tail. A root struct lifts that: each field has independent storage, several fields grow separately, all share the owner's lifetime. Placement rules (local/global only), reference semantics, generic roots, and what roots cannot do (copy, serialize as a whole, live inside another struct).
- [`goose-serialization`](data-modeling/serialization/skill.md) — Serialization — to_bytes / bytes_of / from_bytes, verified loading: > Structures whose links are self-relative offsets are position-independent: saving is a write of bytes, loading a read — no serializer, no schema, no pointer fixup. from_bytes verifies framing, tags, lengths, canonical varints and every link before the bytes become a value; a hostile file gives false and an empty array, never a wild reference.
- [`goose-slot-slice-pools`](data-modeling/slot-slice-pools/skill.md) — slot_pool and slice_pool — lifetimes that do not nest: > When data does not die in scope order (cache entries, graph nodes, open documents), the stdlib's slot_pool<T> hands out reusable slots and slice_pool<T> reusable contiguous runs. free releases no memory and ends no lifetime — every element stays a live, well-typed value; stale references read a replacement value, a logic bug like a stale index, never corruption.
